# Phase 4 — 대규모 리팩토링 (읽기 전용)

[study_list.md §5](../study_list.md#5-레거시--최신-아키텍처-대규모-리팩토링)의 정리.

- **통과 기준**: "지금 이 코드베이스를 재작성해야 하나?"에 사례를 근거로 답할 수 있다 → [§3](#3-적용--절차를-실제-코드베이스에-돌렸다)
- **읽기 전용 트랙**: 대규모 리팩토링은 규모·조직·기간이 조건이라 개인 실습으로 재현되지 않는다. 축소판 실습은 "쉽다"는 잘못된 감각만 남긴다
- **사례 요약은 여기 없다**: 회사 6건의 표·교훈·기간은 [study_list §5](../study_list.md#5-레거시--최신-아키텍처-대규모-리팩토링)에 이미 있다. 이 문서는 그 위에 **판단 절차**를 세우고 **실제 코드베이스에 적용**한다

---

## 이 문서가 하는 일

사례를 다시 요약하는 것은 study_list와 사본을 만드는 일이다. 대신 두 가지를 한다.

- **판단 절차** — 사례에서 뽑은 질문들을 순서 있는 결정 트리로 ([§1](#1-사례에서-뽑은-판단-질문)·[§2](#2-결정-절차))
- **적용** — 손에 있는 실제 코드베이스를 측정해 답을 낸다 ([§3](#3-적용--절차를-실제-코드베이스에-돌렸다)). 대상이 비공개라 **수치는 싣지 않고 방법과 판정 모양만** 남긴다

적용 대상을 고른 이유는 통과 기준이 "이 코드베이스를"이라고 묻기 때문이다. 가상의 코드베이스로는 답이 나오지 않는다.

> 측정 대상은 내가 결정 권한을 가진 코드베이스가 아니다. 아래는 **판단 연습**이며 권고가 아니다.

## 1. 사례에서 뽑은 판단 질문

study_list §5-C의 주의점을 "물어볼 질문" 형태로 바꾸면 이렇게 된다. 각 질문은 실패 사례가 뒷받침한다.

| 질문 | 근거 사례 | 답이 '아니오'면 |
|---|---|---|
| **목표 지점을 말할 수 있는가** | Netscape — 무엇으로 옮길지 없이 처음부터 다시 씀 | 재작성이 아니라 방황이다. 착수하지 않는다 |
| **점진 이행이 물리적으로 가능한가** | Uber — 신·구 앱 동시 번들이 100MB OTA 한도를 넘겨 점진 롤아웃 불가 | 전면 교체로 내몰린다. 롤백 경로가 사라진다 |
| **중간 상태의 유지비를 계산했는가** | Airbnb — 네이티브·RN 두 세계 병존 인프라 비용이 절감분을 잠식 | 이행 중간이 "임시"가 아니라 수년간 유지될 상태가 된다 |
| **기간이 기술 판단으로 정해졌는가** | Uber — 먼저 발표된 날짜가 계획을 지배 | 기술 결정이 아니다. 위험 신호 |
| **기능 개발 중단을 조직이 승인했는가** | LinkedIn — 전사 2개월 전면 중단 후 성공 | 리팩토링이 항상 후순위로 밀린다 |
| **한 번에 하나만 바꾸는가** | Uber — 언어·아키텍처·UX 동시 변경 | 실패 원인을 분리할 수 없다 |
| **안전망이 있는가** | (일반 원칙) 특성화 테스트로 현재 동작 고정 | 리팩토링이 아니라 재작성이다 |
| **DRY·최신 기술이 목적이 되지 않았는가** | Dropbox — 공유 유지 비용 > 두 번 쓰는 비용, 6년 후 철수 | 수단이 목적이 된 상태 |

### 성공 사례는 두 모양뿐이다

study_list §5-E의 기간 표에서 읽어낼 것:

- **2개월 전면 집중** — LinkedIn. 전제는 기능 개발 완전 중단 + 명시적 기간 상한
- **5년 점진** — Shopify. 전제는 경계 설정과 롤백 가능성

그 사이(6개월~1년 반)에 전면 재작성을 시도한 쪽이 대체로 실패했다. *— 6개 사례에서 관측한 패턴일 뿐 통계적 근거는 아니다.*

### Shopify가 말한 "목표는 전부 이행이 아니다"

이 문서의 §5가 기대는 주장이라 원문으로 확인했다.

> **"100% React Native should be an anti-goal."**

네이티브로 남긴 이유도 명시돼 있다.

- **하드웨어 기능** — 2D/3D 스캔, 온디바이스 AI 모델
- **메모리 제약 기능** — 홈·잠금화면 위젯, Apple Watch 앱·컴플리케이션, App Intents, Siri Shortcuts
- **백그라운드 처리** — 장시간 작업(POS 앱의 오프라인 거래 동기화)

그리고 성공했는데도 남은 비용을 적어뒀다. 디버깅이 "flaky", 버전 업그레이드가 "상당한 작업이고 종종 코드베이스 재구조화를 요구", 서드파티 의존 증가로 공급망 공격 표면 확대.

**"native and React Native"**로 생각하라는 것이 결론이다. 성공 사례의 교훈이 "전부 옮겨라"가 아니라 **"경계를 정하라"**다.

## 2. 결정 절차

§1의 질문을 순서대로 물으면 갈림길이 세 개로 정리된다.

```
0. 문제가 무엇인지 측정했는가
   ├─ 아니오 → 측정부터. 여기서 멈춘다  ← 대부분이 여기
   └─ 예
       ▼
1. 목표 지점을 말할 수 있는가 (무엇으로 옮기는가)
   ├─ 아니오 → 착수 금지 (Netscape)
   └─ 예
       ▼
2. 점진 이행이 물리적으로 가능한가 (배포·크기·롤백)
   ├─ 아니오 → 전면 교체밖에 없다. 그 위험을 감당할 조건인지 재검토 (Uber)
   └─ 예
       ▼
3. 중간 상태를 수년간 유지할 비용을 계산했는가
   ├─ 아니오 → 계산부터 (Airbnb)
   └─ 예
       ▼
4. 기능 개발 중단을 조직이 승인했는가
   ├─ 예   → 2개월 전면 집중 모델 (LinkedIn)
   └─ 아니오 → 5년 점진 모델 + 경계 설정 (Shopify)
```

**0번이 이 문서의 핵심이다.** 사례 6건에서 실패한 쪽은 대개 "코드가 더러워 보인다"는 감각에서 출발했다. 감각은 측정이 아니다.

## 3. 적용 — 절차를 실제 코드베이스에 돌렸다

절차 0번부터. 측정한다.

> ⚠️ **측정 대상은 비공개 코드베이스라 수치를 이 저장소에 싣지 않는다.** 아래는 절차를 돌려서 얻은 **방법론적 결과**다. 수치가 없으면 결론을 검증할 수 없다는 점을 감수하고, 대신 **어떻게 측정했는지**를 재현 가능하게 남긴다.

### 무엇을 셌나

절차 0번이 요구하는 최소 측정 항목이다. 어떤 Swift 코드베이스에도 그대로 돌릴 수 있다.

```bash
# 규모 — 생성물을 반드시 분리한다
find . -name '*.swift' -not -path '*/Derived/*' -not -path '*/.build/*' | wc -l

# 프레임워크 혼재 — 이행이 이미 끝났는지 본다
grep -rl 'import SwiftUI' --include='*.swift' . | wc -l
grep -rl 'import UIKit'   --include='*.swift' . | wc -l
grep -rl 'import RxSwift' --include='*.swift' . | wc -l
grep -rl 'await'          --include='*.swift' . | wc -l

# 전역 상태 — 개수가 아니라 격리 방식으로 (아래 §5)
python3 Refactoring/code/phase4/classify_singletons.py <경로>
```

### 측정에서 바로 나온 함정 두 개

- **생성 코드를 빼지 않으면 결론이 뒤집힌다.** 대상 코드베이스는 전체 줄 수의 절반 가까이가 OpenAPI 생성물이었고, 상위 대형 파일이 전부 거기서 나왔다. 그대로 세면 "거대 파일이 많다 → 재작성 후보"라는 **잘못된 결론**이 나온다
- **`import` 수는 화면 비중이 아니다.** `import SwiftUI` 파일이 많다고 화면의 그만큼이 SwiftUI인 게 아니다. 파일 수와 화면 수·트래픽 비중은 다르다. 이건 측정의 한계지 결과가 아니다

### 결과의 모양

수치는 싣지 않지만, **판정의 모양**은 이 문서의 요점이라 남긴다.

- study_list §5-F가 제시한 이행 축 4개 중 **2개는 이미 완료, 1개는 해당 없음, 1개만 부분적으로 남았다**
- 남은 UIKit은 무작위 잔여물이 아니라 **성능·입력 제약 화면에 몰려** 있었다. Shopify가 네이티브로 남긴 범주와 성격이 같다
- 절차 1번("목표 지점을 말할 수 있는가")에서 답이 이상해졌다. **옮겨갈 목표를 대면 그게 지금 상태였다**

결론: **코드 구조 기준으로는 재작성 대상이 아니다.** 그리고 이 답의 범위를 좁히는 것이 §2 절차의 마지막 단계다 — 운영 지표(빌드 시간·크래시율·배포 주기)와 조직 지표(팀 규모·온보딩·리드타임)는 **보지 않았다.** LinkedIn이 움직인 이유는 코드 모양이 아니라 2주마다 터지던 배포 장애였다.

즉 정확한 답은 **"코드 구조 기준으로는 아니다. 운영·조직 지표는 확인하지 않았다"**이다.

## 4. 여기서 배운 것 — 체크리스트가 코드베이스를 가정한다

이번 적용에서 나온 것 중 사례 6건보다 값어치 있는 발견이다.

study_list §5-F의 "iOS 구체 이행 축"(UIKit→SwiftUI, Rx→Concurrency, 싱글톤→DI, 거대 VC 분해)은 **2019년쯤의 레거시 iOS 앱을 암묵적으로 가정한 목록**이다. 그 가정이 이 코드베이스에는 맞지 않았다.

- 4개 축 중 2개는 **이미 완료**, 1개는 **해당 없음**, 1개만 부분적으로 남았다
- 목록만 보고 착수하면 **있지도 않은 문제를 고치려 든다.** UIKit 48개를 "정리 대상"으로 세면, 실제로는 의도된 경계 14개를 부수는 작업이 된다
- 결정 절차 0번을 "측정"으로 둔 이유가 이것이다

[§4-B 비판적 검증](../AI/phase-parallel-ai-verification.md#4-근거-3층과-drift)과 같은 구조다. 파생 요약(체크리스트)을 원본(코드) 대조 없이 근거로 쓰면 틀린다. 이번엔 내가 쓴 체크리스트가 대상이었다.

## 5. 중간 상태인가 정착 상태인가

Airbnb의 교훈은 "중간 상태는 임시가 아니라 수년간 유지될 상태"였다. 그러면 다음 질문이 생긴다. **눈에 보이는 혼재가 이행 부채인가, 의도된 경계인가.**

실측한 세 가지를 이 질문으로 분류해봤다.

| 관측 | 분류 | 근거 |
|---|---|---|
| UIKit 48 파일 (Chat 14) | **정착 상태(경계)** | 성능·입력 제약 화면에 집중. Shopify가 네이티브로 남긴 범주와 성격이 같다 |
| 생성 코드 91,357줄 (48%) | **정착 상태(파이프라인 산출물)** | 손으로 유지하는 코드가 아니다. 다만 생성 스크립트와 어긋나지 않는지는 별도 검사 대상 |
| `static let shared` 다수 | **분류 완료 — 아래 참조** | 개수가 아니라 격리 방식이 판정을 결정한다 |

구분 기준: **"이 상태를 5년 뒤에도 유지할 이유를 말할 수 있는가."** 말할 수 있으면 경계고, 없으면 부채다.

### 전역 상태는 개수가 아니라 격리 방식으로 센다

`static let shared`의 **개수**만 세면 판정에 쓸모가 없다. "싱글톤 스물몇 곳"은 그것이 부채인지 경계인지 말해주지 않는다. Swift 6에서는 actor로 감싼 싱글톤과 검사를 끈 싱글톤이 **완전히 다른 물건**이다.

[`classify_singletons.py`](code/phase4/classify_singletons.py)가 선언을 다섯 갈래로 나눈다.

| 분류 | 판정 |
|---|---|
| `actor` 격리 · `Sendable` 명시 | **경계에 가깝다.** 데이터 경쟁 위험은 언어나 저자 주장으로 처리됐다. 남는 한계는 테스트에서 갈아끼울 수 없다는 것뿐 |
| `@unchecked Sendable` · `nonisolated(unsafe)` | **부채 신호.** [Phase 1b §7](../Concurrency/phase1-concurrency.md#7-통과-기준--sendable과-swift-6-이행)의 기준대로 "락으로 모든 접근을 보호했는가"를 확인해야 정당성이 판단된다 |
| 표시 없음 | **확인 필요.** Swift 6 모드로 빌드해 경고가 나는지 봐야 판정된다 |

실제로 돌려본 코드베이스에서는 **절반 이상이 이미 격리 처리돼 있었다.** §5-F의 "싱글톤 → DI" 축이 암묵적으로 가정한 위험(전역 가변 상태의 데이터 경쟁)이 언어 차원에서 상당 부분 해소돼 있었다는 뜻이다 — [§4](#4-여기서-배운-것--체크리스트가-코드베이스를-가정한다)에서 본 일이 이 축에서도 일어났다.

**판별하려면 더 봐야 하는 것을 "부채"로 미리 세지 않는 것**이 중요하다. 부채 목록이 부풀면 재작성이 정당해 보이기 시작한다.

`[중]` 이 분류기는 세 번 고쳐서 맞았다([§8](#검증하지-못한-것) 아래 사례). 정규식으로 선언을 집는 방식이라 중첩 타입·주석 처리된 선언에서 틀리기 쉽다.

## 7. 스스로 물어볼 것

- 재작성 결정에서 가장 먼저 해야 하는 일은 무엇인가 (§2 절차 0)
- 목표 지점을 말할 수 없을 때 착수하면 무슨 일이 생기는가 (§1 Netscape)
- 점진 이행이 물리적으로 불가능해지는 예를 하나 대라 (§1 Uber)
- 성공 사례의 두 모양과 각각의 전제 (§1)
- Shopify가 네이티브로 남긴 세 범주 (§1)
- 대형 파일 통계를 낼 때 생성 코드를 제외해야 하는 이유 (§3)
- `import` 수를 화면 비중으로 읽으면 무엇이 틀리는가 (§3)
- 혼재가 부채인지 경계인지 가르는 질문 (§5)
- 일반 체크리스트를 코드베이스에 그대로 적용하면 생기는 문제 (§4)

## 8. 검증 기록

### 측정한 것

| 대상 | 방법 | 시점 |
|---|---|---|
| 비공개 코드베이스의 규모·프레임워크 혼재·싱글톤·VC·테스트 | `find`·`grep -rl`·`wc -l` (생성물 제외) | 2026-07-30 |
| 전역 상태의 격리 방식 분류 | `python3 Refactoring/code/phase4/classify_singletons.py <경로>` | 2026-07-30 |

**수치는 이 저장소에 싣지 않는다** — 대상이 비공개다. 명령은 그대로 남겼으니 다른 코드베이스에서 재현할 수 있다.

명령은 `import` 문과 파일 수 기준이다. 재현 가능하지만 **의미는 제한적**이다 — §3의 "뒤집힐 조건"에 적었다.

**틀렸던 것 — 4건**

| # | 내가 쓴 것 | 원문 | 성격 |
|---|---|---|---|
| 1 | Uber: "초기 목표는 9/16" → 11/2 출시 | 9/16은 **사내 테스트**, 10/16 전사 베타, 11/2 공개. 셋 다 크리스마스 앱스토어 동결에서 **역산한 처음부터의 일정**이고 **11/2를 지켰다** | 슬립처럼 읽히게 썼다 |
| 2 | LinkedIn: "IPO 직후에 감행" | `"Six months after their successful IPO in 2011"` | 과장 |
| 3 | LinkedIn: "최고 기술 책임자가 직접 주도" | Kevin Scott, 당시 **VP of Engineering** (Microsoft CTO는 훗날) | 직함 오류 |
| 4 | LinkedIn: "2주마다 배포 장애" | 배포가 **2주에 한 번**이었고, 별개로 프로덕션 장애가 잦았다 | 두 사실을 합쳐 하나로 만들었다 |

**1번이 교훈을 바꾼다.** Uber는 날짜를 못 지켜서 망가진 게 아니다. **날짜를 지키느라 나머지가 전부 휘었다.** 그 날짜는 2015년 말 CEO가 라스베이거스 파티에서 발표한 것이고, 작업 착수는 반년 뒤인 2016년 중반이다. §5-C의 "기간이 먼저 정해진 리팩토링은 위험 신호"는 원문에 더 강하게 뒷받침된다 — 슬립이 아니라 **완주했는데도** 대가를 치렀다.

**놓쳤던 것 — 원문이 더 정확하거나 강한 표현**

- Netscape: `"There never was a version 5.0."` — 5.0을 건너뛴 것 자체가 재작성 좌초의 흔적
- Airbnb: 유지 비용을 "두 세계"가 아니라 **`"we wound up supporting code on three platforms instead of two"`** 라고 적었다. 브리징 인프라가 세 번째 플랫폼이라는 표현이 더 날카롭다
- LinkedIn 성과: 현재 **하루 3회** 배포. 서비스 수 150개(2010) → 750개+(2015)
- 반론 글의 기준: 재작성이 정당한 건 **기술 세대가 바뀐 경우**다. `"Joel is talking about rewriting the same software for the same customers with the same requirements, and most importantly — using the same-generation tools."` 같은 세대 도구로 같은 문제를 다시 푸는 것과, 구식 인프라를 교체하는 것을 구분한다
