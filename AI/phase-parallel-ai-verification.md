- 아래 목록은 표본이 아니라 "발견된 것"의 목록이다. 발견율을 모르므로 "이 정도면 괜찮다"의 근거가 되지 못한다

### 15~24가 앞의 14건과 다른 점

앞 14건은 대체로 **"코드가 틀렸다"**였다. 이번에 늘어난 것 중 절반은 종류가 다르다.

- **17·19·22·24 — 관측 장치가 틀렸다.** 코드가 아니라 *재는 방법*이 틀렸다. 넷 다 "0이 나왔다"로 드러났는데, **0은 '없다'와 '못 쟀다'를 구별해 주지 않는다.** 그래서 17 이후로는 실험에 항상 **양성 대조**를 붙였다 — 초기 렌더 body 수를 따로 찍고(18), 다른 템플릿으로 같은 앱을 기록하고(19), 평범한 `Text`로 플랫폼을 먼저 재봤다(22)
- **21 — 검사 도구가 통과시켰는데 통과가 아니었다.** 6번과 같은 부류이고, 이번엔 **저장소 전체의 검증 근거에 영향**을 줬다. `-typecheck` 으로만 확인한 파일을 다시 `-c` 로 돌려야 했다(결과적으로 추가 진단은 없었다)
- **23 — 요약이 압축되며 각색됐다.** 코드가 아니라 문서다. 넷 다 큰 거짓말이 아니라서 원문을 다시 열지 않으면 안 잡힌다. 셋이 한 사례에 몰려 있었다는 것도 시사적이다 — **한 번 잘못 읽은 출처는 여러 번 틀리게 인용된다**
- **18·20 — 내가 아는 규칙이 낡았다.** 둘 다 "예전에는 맞았던" 통념이다. 프레임워크·컴파일러가 좋아지면 **위반 목록을 외운 쪽이 틀린다**

#### 24가 이 문서에 대해 말해주는 것

24번은 **이 문서에 "0을 받으면 장치를 먼저 의심하라"고 적은 지 30분 뒤에** 났다. 같은 세션, 같은 사람, 방금 쓴 규칙이다.

그리고 대상이 **삭제 판단**이었다. "미커밋 변경 없음"을 근거로 디렉터리 2개를 지우려던 참이었고, 그 0은 git이 `exit 128`로 죽은 값이었다.

읽어낼 것 둘.

1. **체크리스트를 아는 것과 그 순간에 적용하는 것은 다른 일이다.** 규칙을 적어두면 다음에 안 틀린다는 가정이 틀렸다. 그래서 체크리스트는 "기억할 목록"이 아니라 **실제로 한 줄씩 짚는 절차**여야 한다
2. **파괴적 작업 직전이 가장 위험한 지점이다.** 되돌릴 수 없는 일의 근거가 되는 수치는 **한 번 더, 다른 방법으로** 확인한다. 여기서는 git을 믿지 않고 파일 248개의 내용 해시를 히스토리와 직접 대조했고, 그제서야 판단이 근거를 얻었다

`wc -l`·`grep -c`로 결과를 세는 습관 전반이 이 함정을 안고 있다. **실패한 명령의 출력은 대개 0줄이다.** 종료 코드를 안 보면 실패와 "깨끗함"이 같은 값으로 들어온다 — 12번(`grep -c`로 센 싱글톤 개수)도 같은 뿌리다.

### 1·2 — 고치려던 시도도 틀렸다

```swift
let r: Result<String, LoadError> = Result { try load(13) }
// error: invalid conversion of thrown error type 'any Error' to 'LoadError'
```

`Result.init(catching:)`의 시그니처가 `Failure == any Error`로 묶여 있어 typed throws가 흐르지 않는다. 여기서 바로 고치려 한 두 번째 시도도 실패했다.

```swift
let r: Result<String, LoadError> = { do { .success(try load(13)) } catch { .failure(error) } }()
// error: reference to member 'success' cannot be resolved without a contextual type
```

반환 타입이 없는 클로저라 문맥 타입이 안으로 전파되지 않는다. 결국 명시적 함수로 뺐다.

**교훈**: 첫 수정이 통과하지 않았다는 것은 진단이 틀렸을 수 있다는 신호다. 두 번째 에러를 "다른 문제"로 넘기지 말고 이해한 다음에 고친다.

### 4 — 언어 모드에 따라 나타나는 오류

```
error: conformance of 'ExpensiveRow' to protocol 'Equatable'
       crosses into main actor-isolated code and can cause data races
note: main actor-isolated operator function '==' cannot satisfy nonisolated requirement
```

Swift 5 모드에서는 나지 않는다. `-swift-version 6`으로 컴파일했기 때문에 드러났다.

**교훈**: 검증 강도가 낮으면 통과가 통과를 의미하지 않는다. 이 저장소는 그래서 Phase 1 이후 코드를 전부 `-swift-version 6`으로 돌린다.

### 6 — 컴파일러가 잡아주지 못한 유일한 사례

Phase 3에서 Component 토큰이 Semantic을 경유하는지 검사하려고 값을 비교했다.

```
Semantic 경유: 5개 ["button-text-primary", ...]
Primitive 직결: 1개 ["button-bg-primary"]
```

`button-text-primary`는 `Primitive.neutral800`을 직접 가리키는데, 그 값이 `Semantic.surface`와 같아서 "Semantic 경유"로 분류됐다. **코드는 정상 동작했고 결과가 틀렸다.**

- 컴파일도 실행도 통과했다. 출력을 읽고 예상과 다름을 알아차린 것이 유일한 탐지 경로였다
- 검사 *방법* 자체의 결함이라 어떤 자동 수단도 잡지 못한다
- 그래서 문서에 결과를 지우지 않고 **틀린 출력과 왜 틀렸는지를 함께** 남겼다

**교훈**: 검증 도구를 만들었으면 그 도구도 검증 대상이다. "검사기가 통과했다"는 "검사기가 옳다"를 뜻하지 않는다.

### 7 — 로컬에서 되고 원격에서 안 되는 것

`Architecture/README.md` 등 3개 문서가 `ComposableArchitecture/`를 링크했다. 로컬 디스크에는 폴더가 있어서 링크 검사기가 통과시켰다.

```
$ git ls-tree -r --name-only origin/main | grep -c ComposableArchitecture
0
```

폴더가 다른 세션의 **untracked** 상태였다. GitHub에서는 404다.

**교훈**: 파일 존재 검사는 작업트리 기준이다. 공개되는 것은 원격 기준이므로 **커밋·push 상태로 따로 확인**해야 한다. (이 건은 그 세션이 커밋·push해서 해소됐다.)

### 9 — 한 번 측정한 값을 사실로 굳히지 않는다

Phase 1b에서 순차 실행과 `async let`을 비교했다.

```
1회차:  순차 213ms / async let 106ms
2회차:  순차 211ms / async let 110ms
```

**교훈**: 절대값을 인용하면 재현되지 않는다. 문서에는 "타이밍은 실행마다 다르다. 비율이 요점이다"를 함께 적었다. 성능 수치는 조건(하드웨어·부하·코어 수)을 같이 쓰거나 비율만 쓴다.

### 10 — 파생 문서는 낡는다

며칠 전 작성된 정리 문서가 디자인 시스템 컴포넌트 수를 적어놨는데, 실제 소스를 세어 보니 몇 배였다. 이틀 만에 낡은 것이다.

**교훈**: "언제 기준인가"가 적혀 있는 문서는 그 날짜를 신뢰도로 읽어야 한다. 날짜가 없는 문서는 더 위험하다.

| **기대값을 미리 적기** (테스트) | 코드가 아니라 **내 기대가 틀린 것** (15) | 기대와 구현이 같은 오해를 공유하면 둘 다 통과한다 |
| 원격 기준 확인 | 로컬에만 있는 것 (7) | 커밋 내용의 옳음 |
| 전수 검사 스크립트 | 링크·앵커 (8) | 스크립트가 안 보는 축 |
| 재실행 | 재현되지 않는 수치 (9·14) | 항상 같게 틀리는 것 |
| 원본 대조 | 파생 문서의 drift (10), 요약의 각색 (23) | 원본 자체가 틀린 경우 |
| 전수 상태 비교 | 규칙 변경으로 낡은 기대 (11), 부분 불일치 (16) | 비교 대상에 없는 상태 |
| **직접 계측** (호출 수·시간을 센다) | **통념이 낡은 것** (18) | 계측기가 죽어 있으면 그것도 0으로 보인다 (19) |
| **양성 대조** | 관측 장치가 죽어 있는 것 (17·19·22), 실험이 대상을 안 건드린 것 (26) | 대조군까지 같이 죽은 경우 |
| **같은 대상, 다른 도구** | 도구별 검출 범위 차이 (19·21), 한 검사만 통과해 구멍이 드러남 (25) | 두 도구가 같은 맹점을 공유할 때 |
| **종료 코드 확인** | 실패한 명령이 0줄을 뱉은 것 (24) | 종료 코드 0으로 조용히 틀리는 명령 |
| **가정을 실제로 시도** | "못 한다"는 분류가 틀린 것 (27) | 시도 비용이 크면 계속 미뤄진다. 이건 도구가 아니라 습관이라 자동화되지 않는다 |

### 표를 다시 만들면서 나온 것

**이 표 자체가 낡아 있었다.** 사례가 10건에서 24건으로 늘었는데 표는 그대로였고, 대조해 보니 **15번과 18번이 어느 행에도 없었다.** 둘 다 기존 수단으로는 설명되지 않는 종류였기 때문이다.

- **15 — 코드가 아니라 기대가 틀렸다.** 검색어 `"국"`의 결과를 `["KR","US"]`로 적었는데 `영국`도 "국"을 포함한다. 구현은 처음부터 옳았다. 컴파일·실행·출력 읽기 어디에도 걸리지 않는다. **테스트에 기대값을 미리 적어둔 것**만이 이걸 잡는다 — 틀린 쪽이 기대였다는 게 `#expect` 실패 출력으로 드러났다
- **18 — 규칙이 낡았다.** "부모 body 가 돌면 자식도 돈다"는 예전엔 맞았다. 원본 대조로는 안 잡힌다(문서에도 그렇게 적혀 있다). **직접 세는 것**만이 잡는다

두 행을 넣고 나니 사례 1~24가 **전부** 최소 한 행에 들어간다. 넣기 전에는 두 건이 매핑되지 않은 상태였고, 그걸 아무도 알아차리지 못했다.

**그리고 또 늘었다 (2026-07-31, 사례 25~27).** 재귀납 직후에 세 건이 추가됐고, 그중 27번은 기존 행 어디에도 안 들어가서 **행이 하나 더 필요했다** — "가정을 실제로 시도". 재귀납에서 "다음에도 늘어난다고 보는 편이 맞다"고 적어둔 그대로다.

27번은 종류가 다르다. 앞의 26건은 전부 *무엇이 틀렸나*인데, 27번은 **"못 한다"는 판단이 틀린 것**이다. 검사 도구로는 절대 안 잡힌다 — 그 항목은 애초에 검사 대상 목록 밖에 있기 때문이다. 잡은 것은 도구가 아니라 **"왜 필요한데"라는 되물음**이었다.

읽어낼 것:

- **컴파일이 가장 많이 잡는다.** 가장 값싸고 확실한 수단이라 먼저 돌린다
- **6·21 두 건은 자동 수단이 전부 통과했다.** 유형이 다르다 — 대부분은 "틀린 코드", 이 둘은 **"옳게 동작하는 틀린 검사"**다. 그리고 21은 저장소 전체의 검증 근거를 흔들었다. 검사 방법의 결함은 **한 건이 여러 결론을 오염시킨다**
- 사람이 필요한 지점이 명확해진다. **출력을 읽는 일**과 **원본과 대조하는 일**은 위임되지 않는다
- 11·16은 반대 방향의 사례다. **전수 비교를 미리 깔아두면** 규칙을 바꾼 순간 낡은 기대가 자동으로 드러난다. 부분 검증(특정 필드만 확인)에서는 놓친다 ([§2-D §3](../Architecture/phase2d-comparison.md#3-테스트-결정론이-실제-차이다))
- **0을 결과로 받으면 먼저 장치를 의심한다 (17·19·22·24).** "위반 없음"과 "검사가 안 돌았음"은 출력이 같다. 양성 대조를 붙이는 비용이 항상 더 싸다
- **`wc -l`·`grep -c`는 실패를 0으로 바꾼다 (12·24).** 파이프로 세기 전에 종료 코드를 본다. 특히 그 수치가 **삭제·덮어쓰기의 근거**일 때
- **15·18은 "코드가 옳은데 내가 틀린" 경우다.** 앞의 수단은 대부분 *코드*를 검사한다. 이 둘은 검사 대상이 **내 머릿속 기대**였고, 그래서 기대를 밖으로 꺼내 적어야만(테스트 기대값·계측 수치) 대조가 성립했다. 머리에만 있는 기대는 언제나 결과와 일치한다
- **이 표는 파생 요약이고, 따라서 낡는다.** 사례가 두 배 넘게 늘 동안 표는 10건 시점 그대로였다. §4가 남의 문서에 대해 말하는 drift가 **이 문서 안에서 일어났다.** 사례를 추가할 때 §2 행 매핑도 같이 본다

## 3. 실제로 쓴 검증 루프

Phase 0~4에서 굳어진 절차다.

**코드**
- 생성한 코드는 **실행·컴파일 출력으로만** 인정한다. "동작할 것이다"는 근거가 아니다
- 문서에 인용하는 출력은 **실제 출력을 그대로** 붙인다. 손으로 예쁘게 다시 쓰면 그 순간 검증이 아니다
- 언어 모드를 최대로(`-swift-version 6`) 올려 돌린다. 낮은 모드의 통과는 통과가 아니다
- 수치는 재실행해서 변동을 확인한다. 변동하면 비율만 쓴다
- **측정값이 실행마다 달라지면 측정 방법이 틀린 것부터 의심한다.** 사례 14에서 3회 반복이 방법의 결함을 드러냈다. 한 번 돌려 얻은 값은 값이 아니다

**문서**
- 링크·앵커는 스크립트로 전수 검사한다 ([`check_links.py`](code/check_links.py)). 리포의 md 전체를 눈으로 볼 수 없다
- 공개되는 것은 **원격 기준**으로 확인한다 (`git ls-tree origin/main`)
- 인용한 파일은 경로와 확인 날짜를 남긴다. 파생 문서는 낡는다
- **수치는 한 곳에만 둔다.** 인덱스(`README`)에는 "무엇을 찾았나"만 적고 값은 본문을 가리킨다. 같은 숫자를 두 곳에 두면 한쪽이 낡고, 읽는 사람이 어느 쪽이 맞는지 알 수 없다 — 사례 9·10과 같은 실패다

**정직**
- 검증하지 못한 주장은 지우지 않고 **신뢰도 라벨**로 분리한다. 각 문서 마지막 절이 그 자리다
  - `[중]` — 널리 알려졌지만 여기서 측정하지 않음
  - `[저]` — 계획·가설. 아직 해보지 않음
- 틀린 결과가 나오면 지우지 않고 왜 틀렸는지를 함께 남긴다 (사례 6)
- 발견을 **결함으로 단정하지 않는다**. Phase 3에서 대비비 미달을 찾았지만, 디자인 SoT가 따로 있으면 수용된 결정일 수 있어 "판단 유보 + 물어볼 근거"로 적는다

## 4. 근거 3층과 drift

근거는 대개 세 층으로 쌓인다.

```
SoT            정책 문서 · 디자인 원본     ← 요구사항의 원본
   │
구현            코드                       ← 진행된 부분은 여기가 SoT
   │
파생 요약       분석·정리 문서             ← 특정 시점 스냅샷
```

실제로 관측한 drift 2건:

| 무엇 | 파생 문서 | 실물 | 판단 |
|---|---|---|---|
| 컴포넌트 수 | 며칠 전 작성된 정리 문서의 값 | 실제는 몇 배 | **코드가 SoT** → 문서를 근거로 쓰지 않음 |
| Repository 포트 위치 | 교과서 Clean = Domain에 둠 | Core에 두는 배치 (레이어 규칙 때문) | 이유가 코드 주석에 남아 있음 → 판단 가능 |

두 번째가 특히 중요하다. **실물이 교과서와 다를 때 물어볼 것은 "틀렸나"가 아니라 "무엇을 지키려고 무엇을 양보했나"다.** 이유가 코드에 적혀 있으면 판단할 수 있고, 없으면 사고와 구분되지 않는다.

규칙으로 정리하면:

- 요구사항·정책은 **SoT(스펙) 기준**. 구현과 다르면 불일치를 보고한다
- 구조·API는 **코드 기준**. 문서가 다르면 문서가 낡은 것이다
- 파생 요약은 **진입용 색인**으로만 쓴다. 중요한 판단은 원본과 대조한다

## 5. 무엇을 맡기고 무엇을 안 맡겼나

### 잘 맡긴 것

- **병렬 자료 조사** — 독립적인 읽기·검색을 한 번에 묶어 보내는 것. Phase 3에서 디자인 원본·구현 코드·토큰 JSON을 동시에 확인했다
- **기계적 검사 스크립트 작성** — 링크 전수 검사, 대비비 계산, 줄 수·선언 수 집계. 사람이 하면 틀리고 지겹다
- **실행 검증 자체** — 코드를 쓰고 돌려서 출력을 확인하는 루프
- **형식 통일** — 문서 9개가 같은 골격(맥락 → 확인 → 규칙)과 같은 검증 기록 절을 갖는 것

### 안 맡긴 것 / 되돌린 것

- **설계 판단** — Phase 0에서 만든 컴포넌트 API가 실제 채택된 것과 달랐다. 둘 다 맞고 전제가 달랐다. 어느 전제가 이 프로젝트에 맞는지는 제품·조직 정보가 필요하다
- **결함 확정** — 대비비 미달을 찾았지만 확정하지 않았다. 디자인 SoT가 따로 있고 의도된 수용일 수 있다
- **남의 작업 push** — 병행 세션의 커밋을 발견했지만 대신 올리지 않았다. 검토하지 않은 작업을 공개하는 일이고, 그쪽이 아직 쓰는 중이었다
- **파괴적 정리** — worktree 삭제 전에 세 가지(조상 포함 여부·미커밋 변경·미반영 커밋)를 확인하고 나서 실행했다

경계는 하나로 요약된다. **되돌릴 수 있고 검증 가능한 일은 맡긴다. 되돌리기 어렵거나 판단이 필요한 일은 근거를 만들어 올린다.**

## 6. 컨텍스트 설계 — 이 워크스페이스가 교재다

§4-A에서 배울 것이 문서가 아니라 여기 있다.

**신뢰도와 최신성을 문서가 스스로 밝힌다**

- 반대 관점도 남긴다. `07` §3은 경량 MVVM을 고르면서 "exhaustive 테스트가 목표면 TCA가 더 옳을 수 있다"를 같이 적었다

**구조가 참조를 짧게 만든다**
- 이 저장소를 study_list 묶음별 폴더로 나눈 뒤, 문서 간 링크가 `../Concurrency/phase1-concurrency.md`처럼 예측 가능해졌다
- 폴더마다 `README.md`가 인덱스라 진입점이 하나다

**병행 작업**
- 병행 세션과 충돌을 피하려고 worktree를 썼다. 파일 집합이 겹치지 않으면 rebase가 깨끗하다는 것을 실제로 확인했다(`merge-tree`로 사전 검사 → 충돌 0)

## 자동화한 것과 안 한 것

[study_list §4-A](../study_list.md#4-a-활용)가 자동화 대상 네 가지를 적어놨다. Phase 0~4를 마친 시점에 **실제로 무엇을 자동화했는지** 대조한다. 넷 중 둘은 했고, 하나는 부분, 하나는 안 했다.

| §4-A 항목 | 실제로 한 것 | 산출물 |
|---|---|---|
| 디자인 토큰 → 코드 파이프라인 | **안 했다.** 남의 파이프라인을 읽기만 했다 | — ([Phase 3 §2](../DesignSystem/phase3-design-system.md#파이프라인--생성물을-커밋할-것인가)) |
| 스펙 → 테스트 케이스 | **했다.** 감사표의 대비비를 회귀 가드로 옮김 | `AccessibilityTests.swift` (131줄) |
| 코드리뷰 보조 | **부분.** 리뷰가 아니라 **규칙 강제**를 자동화 | `verify_layering_guard.sh` (96줄) · `check_links.py` (80줄) |
| 기계적 마이그레이션 | **안 했다.** Swift 6 이행은 진단을 하나씩 손으로 고쳤다 | ([Phase 1b §7](../Concurrency/phase1-concurrency.md#이행을-실제로-해봤다-2026-07-31)) |

*(줄 수는 2026-07-31 `wc -l`, 종료 코드 확인함 — 사례 24)*

### 스펙 → 테스트가 가장 값이 컸다

[Phase 3 §4](../DesignSystem/phase3-design-system.md#실제로-닫은-것-2026-07-31)에서 한 일이 이 항목의 전형이다. 대비비 감사는 원래 `DESIGN.md`의 hex를 손으로 계산한 **일회성 표**였다. 그걸 팔레트의 실제 `Color`에서 성분을 꺼내 계산하는 테스트로 옮겼다.

바뀐 것: 스펙 문서에 적힌 값이 **코드가 지키는 조건**이 됐다. 토큰이 바뀌면 계산도 따라 바뀐다. 문서와 코드가 어긋날 수 없다.

이게 §4의 drift 문제에 대한 유일한 구조적 해법이다. **문서에 적힌 사실을 실행 가능한 검사로 옮기면 그 사실은 낡지 않는다.** 옮길 수 없는 사실(설계 의도, 왜 그렇게 했나)만 문서에 남는다.

### 자동화하지 않은 둘, 그 이유

**토큰 파이프라인** — 원본이 다른 저장소에 있고 디자인 도구가 SoT다. 여기서 생성 스크립트를 돌리면 남의 저장소의 생성물을 덮어쓰게 된다. 읽고 구조를 정리하는 데서 멈춘 것은 §5의 "안 맡긴 것"과 같은 경계다.

**기계적 마이그레이션** — Swift 6 이행은 자동화하려다 안 했다. 이유가 명확했다. [사례 20](#1-실제로-틀렸던-것들)에서 **내가 위반이라고 예상한 5곳 중 1곳이 위반이 아니었다.** 일괄 치환 스크립트를 짰다면 그 1곳에 불필요한 `@unchecked Sendable`이나 격리 표기를 붙였을 것이고, 컴파일은 통과했을 것이다. 진단을 하나씩 읽는 편이 옳았다.

일반화하면: **컴파일러가 대상을 정확히 짚어주는 작업은 자동화 이득이 작다.** 이득은 대상을 *찾는* 데 있는데 그건 이미 공짜다.

### 자동화는 검증 대상을 하나 더 만든다

여기가 4-A와 4-B가 만나는 지점이다. 이 리포에서 만든 검사 도구 다섯 개 중 **세 개에서 도구 자체의 결함이 나왔다.**

| 도구 | 무엇이 틀렸나 | 사례 |
|---|---|---|
| `token_audit.swift` | 값 비교로 참조 경로를 판정 — 값이 같으면 구분 못 함 | [6](#6--컴파일러가-잡아주지-못한-유일한-사례) |
| `check_links.py` | 앵커 slug 규칙이 GitHub 실제 규칙과 같은지 미대조 | [§9](#확인하지-못한-것) |
| `classify_singletons.py` | 주석 처리된 선언·의존성 소스가 섞임. **3번 고쳐야** 맞았다 | 12 |

세 건 모두 **도구는 정상 종료했고 출력이 틀렸다.** 컴파일도 실행도 통과한다.

그래서 자동화의 손익은 이렇게 계산해야 한다.

```
이득 = (사람이 반복할 비용) − (도구를 만드는 비용) − (도구를 검증하는 비용)
                                                       ↑ 이 항을 빼먹는다
```

`check_links.py`는 리포의 md 전체를 검사한다 — 사람이 못 하는 규모라 세 번째 항을 치르고도 남는다. `classify_singletons.py`는 25개를 분류하는 데 3번 고쳤다 — 눈으로 훑는 것과 비슷한 비용이었고, 실제로 **결국 눈으로 훑어서** 틀린 걸 찾았다.

**규모가 작으면 자동화가 손해다.** 그리고 규모가 작을수록 도구의 결함을 알아차리기도 어렵다 — 출력이 짧아서 "그럴듯하면" 넘어간다.

### 가드는 일부러 깨뜨려 본 것만 가드다

만든 검사기 중 **양성 대조를 붙인 것**과 아닌 것이 갈린다.

- `verify_layering_guard.sh` — 위반을 일부러 넣어 가드가 잡는지 확인했다 ([§2-B](../Architecture/phase2-clean-layered.md#2-경계는-선언만으로-지켜지지-않는다))
- 스냅샷 — 토큰 하나를 깨뜨려 3건이 실패하는 것을 확인했다 ([Phase 3 §5](../DesignSystem/phase3-design-system.md#붙였다-2026-07-31))
- `token_audit.swift` — **안 붙였다.** 그래서 사례 6이 났다

셋의 차이가 결과의 차이와 정확히 일치한다.

## 7. 체크리스트

작업 끝에 이 순서로 확인한다.

**코드를 썼다면**
- [ ] 컴파일·실행했고 출력을 봤다
- [ ] 언어 모드를 최대로 올려 돌렸다
- [ ] **모드만이 아니라 명령도 맞는지 봤다** — `-typecheck`은 SIL 패스 진단을 놓친다. 검증은 `-c`나 `swift build`로 (21)
- [ ] 문서에 인용한 출력이 실제 출력과 글자 단위로 같다
- [ ] 수치를 인용했다면 재실행해서 변동을 확인했다
- [ ] 검사 스크립트를 만들었다면, 그 스크립트가 옳은지도 확인했다

**측정·실험을 했다면**
- [ ] **0이 나왔을 때 장치가 살아 있는지 먼저 확인했다** — "없다"와 "못 쟀다"는 출력이 같다 (17·19·22)
- [ ] 양성 대조를 붙였다 — 반드시 검출돼야 하는 것을 일부러 넣어 봤다
- [ ] 가드를 만들었다면 **일부러 깨뜨려** 실제로 잡는지 봤다 (스냅샷·레이어 가드)
- [ ] 실험 설계가 측정하려는 것을 실제로 건드리는지 확인했다 (17)

**문서를 썼다면**
- [ ] 링크·앵커를 전수 검사했다 (`python3 AI/code/check_links.py`)
- [ ] 공개되는 링크를 원격 기준으로 확인했다
- [ ] 인용한 외부 파일에 경로와 확인 날짜를 남겼다
- [ ] 검증하지 못한 주장에 신뢰도 라벨을 붙였다
- [ ] 발견을 결함으로 단정하지 않았다. SoT가 무엇인지 확인했다
- [ ] **요약을 인용했다면 원문을 다시 열었다** — 요약은 압축되며 각색된다 (23). 특히 날짜·직함·"직후" 같은 부사

**커밋·push 전**
- [ ] 내가 만든 것과 남의 작업이 섞이지 않았다
- [ ] 되돌리기 어려운 작업(force push·삭제) 전에 잃을 것이 없음을 확인했다
- [ ] **그 확인의 근거가 된 수치를 다른 방법으로 한 번 더 얻었다** — 첫 방법이 조용히 실패했을 수 있다 (24)
- [ ] 세는 명령(`wc -l`·`grep -c`)을 썼다면 **종료 코드를 봤다** (12·24)

| 대상 | 명령 | 결과 |
|---|---|---|

| 링크 검사기 (2026-07-31) | 같음 | **md 119개 / 깨진 경로 0 / 깨진 앵커 0, exit 0.** 미완 9건은 그 사이 전부 채워졌다 |
| §2 표의 사례 매핑 (2026-07-31) | 표에서 `(n)` 패턴을 뽑아 1~24와 차집합 | 재귀납 **전**: 15·18 누락. **후**: 누락 0, 24 초과 인용 0 |

`check_links.py`가 보고하던 미해결 건은 병행 세션의 TCA 문서가 아직 만들지 않은 섹션을 미리 링크한 것이었다. 섹션이 채워지는 대로 줄어들 것이라고 적었고, **9 → 6 → 0으로 실제로 그렇게 됐다.**

**건수를 문서에 박아두지 않는다.** 처음엔 "9건"이라고 적었는데 이틀도 안 지나 6건이 됐고 지금은 0건이다. 검사 대상 문서 수도 46 → 119로 늘었다 — 위 표의 첫 행이 그 사이 낡아 있었고, **이번에 다시 돌려서야 알았다.** 사례 9·10과 같은 이유이고, 같은 실패가 이 문서 안에서 반복된 기록이다.

### 확인하지 못한 것

| 주장 | 상태 |
|---|---|
| 오류 발견율 | **측정 불가**. 못 잡은 오류의 수를 모른다 (머리말) |
| §2 표의 "못 잡는 것" 열이 완전한지 | **미검증 [저]**. 24건에서 귀납한 것이고 빠진 유형이 있을 것이다. 10건 → 24건 재귀납에서 **행 2개가 새로 필요했으므로**, 다음 재귀납에서도 늘어난다고 보는 편이 맞다 |
| §2 표가 사례를 빠뜨리지 않았는지 | **확인함 (2026-07-31)**. 사례 번호 1~24를 행별 인용과 대조해 전부 최소 한 행에 들어가는 것을 확인. 재귀납 전에는 15·18이 누락돼 있었다 |
| `check_links.py`의 앵커 slug 규칙 | **근사 [중]**. GitHub 실제 규칙과 완전히 같은지 대조하지 않았다. 이모지·특수문자가 섞인 제목에서 어긋날 수 있다 |
| §6의 컨텍스트 설계가 효과적이었는지 | **주관 [저]**. 비교군이 없다 |

세 번째 항목이 사례 6과 같은 종류다. **검사기 자체가 검증되지 않았다**는 것을 적어둔다.

## 미검증 대장 — 저장소 전체

문서 8개가 각자 "확인하지 못한 것" 표를 갖고 있다. 개별 문서를 읽을 때는 그게 맞지만, **저장소 전체에서 무엇이 안 닫혀 있는지**는 아무 데서도 안 보였다.

여기는 **색인**이다. 항목 내용과 수치는 각 문서에 있고 여기 옮기지 않는다 — [§3의 "수치는 한 곳에만"](#3-실제로-쓴-검증-루프)이 그 이유다. 사례 10이 정확히 이 실패였다.

### 왜 안 닫혔나로 묶으면

| 원인 | 성격 | 어디에 있나 |
|---|---|---|
| **플랫폼이 없다** | macOS에서 빌드하므로 UIKit·Dynamic Type이 존재하지 않는다. 코드를 고쳐서 닫을 수 없다 | [Phase 1a](../Swift/phase1-swiftui-rendering.md#확인하지-못한-것) · [Phase 3](../DesignSystem/phase3-design-system.md#확인하지-못한-것) · [Phase 0](../Swift/phase0-language-core.md#검증하지-못한-것) |
| **도구가 응답하지 않는다** | Instruments SwiftUI 템플릿이 이 조합에서 데이터를 내지 않는다. 우회했고 두 측정이 일치한다 | [Phase 1a](../Swift/phase1-swiftui-rendering.md#확인하지-못한-것) |
| **규모가 없다** | 화면 1개·파일 1개·혼자. 대규모에서만 나타나는 성질은 관측 대상이 아예 없다 | [Phase 1b](../Concurrency/phase1-concurrency.md#확인하지-못한-것) · [§2-A](../Architecture/phase2-mvvm.md#확인하지-못한-것) · [§2-B](../Architecture/phase2-clean-layered.md#확인하지-못한-것) · [§2-C](../Architecture/phase2c-tca.md#확인하지-못한-것) · [§2-D](../Architecture/phase2d-comparison.md#확인하지-못한-것) |
| **안 돌렸다** | `xcodebuild`·생성 스크립트·프리뷰. **할 수 있는데 안 한 것** — 이 묶음만 마음먹으면 줄어든다. 실제로 TSan·`.equatable()` 두 건은 2026-07-31에 이 묶음에서 빠져나갔다 | [Phase 1b](../Concurrency/phase1-concurrency.md#확인하지-못한-것) · [Phase 3](../DesignSystem/phase3-design-system.md#확인하지-못한-것) · [Phase 4](../Refactoring/phase4-large-scale-refactoring.md#검증하지-못한-것) |
| **접근이 막혔다** | 유료 장벽·403·SoT가 다른 곳에 있음. 2차 출처로 대조했거나 판단을 유보했다 | [Phase 4](../Refactoring/phase4-large-scale-refactoring.md#검증하지-못한-것) · [Phase 3](../DesignSystem/phase3-design-system.md#확인하지-못한-것) |
| **원리적으로 불가** | 팀 온보딩 비용, 오류 발견율. 조건 자체가 성립하지 않는다 | [§2-C](../Architecture/phase2c-tca.md#확인하지-못한-것) · [§2-D](../Architecture/phase2d-comparison.md#확인하지-못한-것) · [머리말](#가장-중요한-한계를-먼저) |
| **문서·통념 기반** | 널리 알려진 동작을 여기서 재지 않고 인용한 것. `[중]` 라벨이 대부분 여기 | 전 문서 |

### 이 묶음이 말해주는 것

- **"안 돌렸다"만 자력으로 줄어든다.** 나머지 다섯은 환경·규모·권한이 바뀌어야 닫힌다. 다음 사이클을 계획할 때 이 구분이 우선순위 그 자체다
- **분류 자체가 틀릴 수 있다.** TSan과 `.equatable()`은 "실행 환경이 필요해서 못 한다"로 적혀 있었는데, 실제로는 이 환경에서 되는 것이었다. **못 하는 이유를 적어두면 그 이유가 맞는지도 검사 대상이 된다** — 적어두지 않았으면 영영 안 했다
- **"플랫폼이 없다"가 가장 위험한 묶음이다.** 코드가 컴파일되기 때문에 닫힌 것처럼 보인다. [사례 22](#1-실제로-틀렸던-것들)(`@ScaledMetric`이 macOS에서 아무것도 안 함)가 그 함정에 실제로 빠진 기록이다
- **`[중]` 라벨이 가장 조용하다.** "널리 알려진 동작"은 [사례 18·20](#1524가-앞의-14건과-다른-점)처럼 **낡는다.** 통념을 인용할 때 라벨을 붙이는 이유가 이것이고, 붙여둔 것만이 나중에 다시 볼 대상이 된다

### 개수를 여기 적지 않는 이유

세면 낡는다. 실제로 각 문서에서 **해소된 항목은 취소선으로 남아 있고**(`~~...~~ **해소 (2026-07-31)**`) 새 항목은 계속 추가된다. 총계를 여기 박아두면 두 사본이 어긋나고, 그게 이 문서가 §4에서 경계하는 바로 그 drift다 — [사례 9·10](#1-실제로-틀렸던-것들), 그리고 [§2 표가 실제로 낡았던 것](#표를-다시-만들면서-나온-것).

**세고 싶으면 각 문서를 열어서 센다.** 그게 이 색인의 용도다.
