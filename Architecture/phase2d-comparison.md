## 먼저 한계를 긋는다

**C는 TCA 라이브러리가 아니다.** Point-Free ep68~71·83~84가 라이브러리 이전에 손으로 만들어 보이는 형태를 최소로 재현한 것이다. 그래서 비교할 수 있는 축과 없는 축이 갈린다.

| 축 | 측정 가능한가 | 이유 |
|---|---|---|
| 화면당 코드량 | ✅ 패턴 수준에서 | 리듀서·액션·상태 구조는 라이브러리 없이도 같다 |
| 비즈니스 규칙의 위치 | ✅ | 설계 결정이라 라이브러리와 무관 |
| 테스트 결정론 | ✅ | 효과를 값으로 반환하는 구조가 만드는 성질 |
| 컴파일 시간 | ❌ → ✅ | 실제 비용은 라이브러리의 제네릭·매크로에서 온다. 여기엔 그게 없다 |
| 러닝커브 | ❌ → ✅ | 라이브러리 API 표면을 재현하지 않았다 |
| lock-in·버전 종속 | ❌ → 🟡 | 의존성이 없다 |

측정 못 하는 축을 "차이 없음"으로 적으면 안 된다. 그래서 아래 표에는 세 축만 수치가 있다.

> **갱신 (2026-07-31)** — 아래 세 축은 이후 [§2-C](phase2c-tca.md)에서 **TCA 1.26.1 실물을 붙여 측정했다.** 이 문서의 "측정 불가" 서술은 최소 재현본 기준이며, 실물 수치는 [§2-C §5](phase2c-tca.md#5-비용--실측)에 있다. 요약하면 컴파일 시간은 **증분 9.51s vs 1.15s로 판별됐고**, 러닝커브 프록시는 **9개 → 22개**였다.

## 1. 세 번째 구현 — Reducer + Store

### 형태

```swift
struct Effect<Action: Sendable>: Sendable {
    let run: @Sendable () async -> Action?      // 부수효과를 '값'으로 반환한다
}

typealias Reducer<State, Action: Sendable, Environment> =
    (inout State, Action, Environment) -> [Effect<Action>]
```

핵심은 리듀서가 효과를 **실행하지 않고 반환**하는 것이다. 실행 시점을 호출자가 정하므로, 테스트가 그 시점을 통제할 수 있다. [§3](#3-테스트-결정론이-실제-차이다)의 모든 성질이 이 한 줄에서 나온다.

### Environment는 프로토콜이 아니라 함수를 담은 구조체

```swift
struct CountryEnvironment {
    var loadCountries: @Sendable () async -> Result<[Country], LoadFailure>
    var preferredCode: String = "KR"
}
```

[§2-B](phase2-clean-layered.md#3-포트를-어디-두는가--교과서가-지는-사례)의 Repository 프로토콜과 대비된다.

- 프로토콜: 목을 만들려면 **타입을 새로 선언**해야 한다 (`StubCountryRepository`)
- 함수 구조체: **클로저만 갈아 끼운다**. `CountryEnvironment { .success(stubbed) }`

테스트에서 타입 선언이 사라지는 게 이 선택의 실익이다. 대신 컴파일러가 "이 의존성을 구현했는가"를 프로토콜만큼 강하게 묻지 않는다.

### 확인 — 동작이 A·B와 같다

```
[C-1] 실서비스 경로
  로딩 시작: isLoading=true
  첫 시도 실패: error=목록을 불러오지 못했어요.
  재시도 성공: ["KR", "US", "GB", "JP"]
  '국' 필터: ["KR", "US", "GB"]
```

A·B와 글자 단위로 같다([§2-B §5](phase2-clean-layered.md#5-확인--같은-화면을-clean으로)의 출력과 대조). 세 방식의 차이는 관측 동작이 아니라 구조에만 있다.

## 2. 비교 축 — 수치

### 화면당 코드량

주석·빈 줄을 제외하고 소스의 마커 구간을 파싱해 실측했다.

| | 화면 코드 | 선언 | 일회성 인프라 |
|---|---|---|---|
| **A** 경량 단방향 MVVM | **54줄** | 3 | — (`Tasker` 별도) |
| **B** Clean + MVVM | **83줄** | 9 | — |
| **C** Reducer + Store | **53줄** | 3 | 코어 23줄/3선언 + TestStore 42줄/1선언 |

**예상과 다른 결과가 나왔다.** C의 화면 코드가 A와 거의 같다(53 vs 54).

- "TCA는 보일러플레이트가 많다"는 통념은 **화면당 코드량 축에서는 이 규모에서 확인되지 않았다**
- C의 추가 비용은 코어 23줄 + 테스트 하네스 42줄인데, 이건 **화면 수와 무관하게 한 번** 낸다. 실제 TCA에서는 라이브러리가 대신 낸다
- 화면이 늘면 A·C는 비슷하게 늘고, B는 화면마다 UseCase·Repository가 붙어 더 빨리 늘 것으로 보인다. *— 화면 1개만 만들어봤으므로 추정이다*

단, 실제 TCA는 내 최소 구현보다 화면당 의식이 많다(`@Reducer` 매크로, `Store` 바인딩, `ViewStore` 등). 이 수치를 라이브러리 비용의 근거로 쓰면 안 된다.

### 비즈니스 규칙이 사는 곳

정렬 규칙(선호 국가 최상단) 하나가 세 방식에서 다른 자리에 앉는다.

| | 위치 | 결과 |
|---|---|---|
| A | `State.visible` 계산 프로퍼티 | 화면 상태와 규칙이 한 타입에 섞인다 |
| B | `FetchCountriesUseCase` | 규칙만 단독 테스트된다 |
| C | 리듀서의 `.response(.success)` 분기 | 상태 변경 지점에 규칙이 있다. 액션 흐름으로 추적된다 |

세 위치 모두 정당하고, 무엇을 쉽게 만드는지가 다르다. B는 규칙 단독 검증, C는 규칙이 언제 적용되는지 추적, A는 코드 최소화.

### 테스트 결정론 — 유일하게 결정적인 차이

| | 비동기 완료를 기다리는 방법 | 전수성 |
|---|---|---|
| A | `Tasker.wait(key)`를 **직접 만들어야 했다** | 없음 |
| B | 같음 (A와 동일 구조) | UseCase 단독 검증은 가능 |
| C | **필요 없다.** 효과가 값이라 테스트가 실행 시점을 정한다 | 상태·액션·잔여 효과 전부 |

자세한 내용은 [§3](#3-테스트-결정론이-실제-차이다).

### 컴파일 시간 — 이 규모에서는 답이 안 나온다

`swiftc -typecheck -swift-version 6`을 3회씩 측정했다.

```
mvvm_vs_clean.swift (A+B):  0.33s / 0.28s / 0.30s
three_way.swift     (C):    0.23s / 0.22s / 0.25s
```

- 실행 간 편차가 0.05s인데 두 파일 차이가 0.06s다. **판별되지 않는다**
- 애초에 파일이 변형별로 분리돼 있지 않아 공정한 비교도 아니다
- 실제 TCA의 컴파일 비용은 라이브러리의 제네릭·매크로에서 오고, 내 최소 구현에는 그게 없다

**이 축은 실제 프로젝트에서 라이브러리를 붙여 재보는 수밖에 없다.** 여기서 "차이 없음"이라고 적으면 거짓이 된다.

> **닫혔다 (2026-07-31)** — [§2-C](phase2c-tca.md)에서 TCA 1.26.1을 실제로 붙여 측정했다.
>
> | | 시간 |
> |---|---|
> | TCA 증분 빌드 (리듀서 1파일 수정) | **9.51s** |
> | 손코딩 단일 파일 전체 컴파일 | **1.15s** |
> | TCA 클린 빌드 (의존성 14개 포함) | 75.07s |
>
> **8배 차이로 판별됐다.** 위 `-typecheck` 수치가 답을 못 낸 이유는 규모가 아니라 **매크로가 없었기 때문**이다. 상세는 [§2-C §5](phase2c-tca.md#빌드-시간).

### 온보딩 비용 — 새 개념 수 (프록시)

| | 새로 익혀야 하는 개념 | 개수 |
|---|---|---|
| A | State · Action · `sendAction` · Tasker | 4 |
| B | + Entity · Repository 포트 · Live/Stub · UseCase | 8 |
| C | + Effect · Reducer · Store · Environment · 보낸/받은 액션 구분 | 9 |

개념 수는 러닝커브의 **프록시일 뿐**이다. 실제 어려움은 개수가 아니라 낯섦에서 오고, C의 "효과를 값으로 반환한다"는 하나가 A의 네 개보다 넘기 어려울 수 있다.

> **실물 수치 (2026-07-31)** — [§2-C](phase2c-tca.md)에서 같은 화면을 TCA 1.26.1로 만드는 데 실제로 쓴 API는 **22개**였다. 위 표의 `C = 9`는 최소 재현본 기준이라 **실물의 40%밖에 안 된다.** 그것도 `TestClock`·`Shared`·`NavigationStack` 계열을 안 썼을 때다. 목록은 [§2-C §5](phase2c-tca.md#러닝커브--새-api-표면-프록시).

## 3. 테스트 결정론이 실제 차이다

### A·B에서 무엇이 필요했나

`sendAction`은 즉시 반환하고 실제 작업은 `Tasker`가 돌린다. 테스트가 결과를 보려면 완료를 기다려야 하는데 그 창구가 없어서 직접 만들었다.

```swift
/// 테스트에서 완료를 기다리기 위한 창구. 실제 코드에는 없다.
func wait(_ key: String) async { await tasks[key]?.value }
```

### C는 기다리지 않는다

```
[C-2] TestStore — 대기 없이 전수 검증
  실패 0건 — 전부 기대와 일치
  Task.sleep 호출 0회. 효과 실행 시점을 테스트가 정한다
```

```swift
store.send(.appeared) { $0.isLoading = true }
await store.receive(.response(.success(stubbed))) {
    $0.isLoading = false
    $0.countries = sortedStubbed
}
store.send(.queryChanged("국")) { $0.query = "국" }
store.finish()
```

`send`와 `receive`가 나뉘어 있는 것이 요점이다. ep84가 "보낸 액션과 받은 액션의 구분"에 가장 많은 시간을 쓴 이유다 — **보낸 것은 사용자 행동이고 받은 것은 네트워크·디스크 결과**다. 테스트가 그 둘을 구분해 적으면 흐름이 문서가 된다.

### 전수성을 실제로 검증했다

틀린 기대를 일부러 넣어 잡아내는지 봤다.

```
[C-3] 전수성 — 틀린 기대와 빠뜨린 효과를 잡는다
  (a) 상태 기대 오류 → 검출 1건: send(appeared) 후 상태 불일치
  (b) 액션 기대 오류 → 검출 2건: 받은 액션 불일치: 기대 response(.success, 4개), 실제 response(.failure(network))
  (c) 효과 누락 → 검출 1건: 처리하지 않은 효과 1개가 남았다
```

(c)가 A·B에 없는 성질이다. **처리하지 않은 효과가 남으면 실패**시키므로, "네트워크 호출이 하나 더 나가는데 테스트는 통과"하는 상태가 생기지 않는다.

### 작업 중 실제로 겪은 일

정렬 규칙을 C의 리듀서에 추가한 직후 테스트가 깨졌다.

```
실패 1건 — receive(response(.success, 4개)) 후 상태 불일치
```

기대값이 정렬 이전 배열이라 낡은 것이었다. **규칙을 바꾼 순간 기대가 낡았고 즉시 검출됐다.** 전수 상태 비교가 하는 일이 이것이고, 부분 검증(특정 필드만 확인)에서는 놓칠 수 있는 종류다.

### ep85의 결론과 맞물린다

병행 세션의 [05 Testing 정리](ComposableArchitecture/05-testing/00-overview.md)에 따르면 ep85는 바닐라 SwiftUI로 같은 테스트를 시도하고 이렇게 막힌다.

| 대상 | 막히는 지점 |
|---|---|
| `@ObservedObject` 카운터 | `AppState`가 클래스라 멤버와이즈 이니셜라이저도 `Equatable` 합성도 없다 |
| `@State` 카운터 | **근본적으로 안 된다.** `@State`가 `UIHostingController` 맥락을 요구한다 |

그리고 결론이 "시도한 모든 것이 로직을 뷰 밖으로 빼고, `@State`를 앱 상태로 올리고, 상태를 값 타입으로 묶으라고 요구했다"는 것이다.

**내가 A에서 `Tasker.wait`를 손으로 만든 것이 같은 압력의 작은 버전이다.** 테스트 가능성을 원하면 구조가 특정 방향으로 밀린다. A는 그 방향으로 절반쯤 가 있고(State struct·Action enum·`private(set)`), 결정론만 빠져 있었다.

## 4. 종합 — 어떤 상황에 무엇을

| 상황 | 선택 | 근거 |
|---|---|---|
| 화면이 적고 상태 전이가 단순 | **A** | 개념 4개, 화면 코드 최소. 규율은 `private(set)`으로 강제 |
| 서버 스키마가 자주 바뀐다 | **B** | 매핑 경계 하나만 고친다 ([§2-B §4](phase2-clean-layered.md#4-dto--domain-매핑-위치)) |
| 비즈니스 규칙을 단독 검증해야 한다 | **B** | UseCase가 화면 없이 테스트된다 |
| 상태 머신이 많고 정책 회귀를 막아야 한다 | **C** | 전수 검증 + 효과 누락 검출 |
| 부수효과가 많고 순서가 중요하다 | **C** | 보낸/받은 액션 구분이 흐름을 고정한다 |
| 팀이 라이브러리 학습·버전 추종 비용을 감당하기 어렵다 | **A** 또는 **C의 패턴만** | 리듀서 사고방식은 라이브러리 없이 채택 가능 (코어 23줄) |

마지막 줄이 이번 실습의 실용적 결론이다. **"TCA를 쓴다"와 "리듀서 패턴을 쓴다"는 분리 가능하다.** `07-ios-project-guide.md` §3이 경량 MVVM을 고르면서 "핵심 상태 머신만 reducer 스타일로"를 남긴 것과 같은 판단이고, 코어 23줄이면 된다는 것을 실측으로 확인했다.

## 5. 모듈화

§2-D의 나머지 절반. 여기는 실습 규모로 재현되지 않는 영역이라 **판단 기준만** 정리한다.

| 축 | 선택지 | 무엇이 갈리나 |
|---|---|---|
| DesignSystem의 위치 | Core 안에 두기 / Core와 **형제**로 분리 | 형제로 빼야 `Core ↛ DesignSystem`을 규칙으로 강제할 수 있다 |
| 순환 차단 | 빌드 시스템에 맡기기 / 별도 가드 추가 | 빌드는 순환만 막는다. **형제 간 방향**은 안 막는다 |
| 피처 독립 실행 | 앱만 / 피처별 Example 앱 타깃 | 앱 전체를 띄우지 않고 한 모듈만 실행할 수 있는가 |

읽어낼 것:

- **순환 의존은 빌드 시스템이 공짜로 막아준다.** SPM/Xcode가 거부한다. 별도 도구가 필요한 건 **형제 간 방향**(`Core → DesignSystem`)이고, 그건 import grep 백 줄이면 강제된다 ([§2-B §2](phase2-clean-layered.md#2-경계는-선언만으로-지켜지지-않는다))
- **DesignSystem을 분리하면 Example 앱 타깃이 따라온다.** 앱 전체를 띄우지 않고 컴포넌트만 실행한다. 컴포넌트가 수십 종이 되면 이게 없으면 카탈로그를 확인할 방법이 없다 ([Phase 3 §5](../DesignSystem/phase3-design-system.md#5-카탈로그와-테스트))
- **레이어 수는 본질이 아니다.** 의존 방향이 지켜지는지가 전부다. 같은 원칙 위에서 한 축만 다르게 그은 배치는 얼마든지 있다

`[저]` 이 표는 판단 축이지 측정이 아니다. 모듈 수에 따른 빌드 시간·의존 그래프 복잡도는 재지 않았다.

## 7. 스스로 물어볼 것

- 리듀서가 효과를 실행하지 않고 반환하면 테스트에서 무엇이 가능해지는가 (§1)
- Environment를 프로토콜이 아니라 함수 구조체로 두면 무엇을 얻고 무엇을 잃는가 (§1)
- 정렬 규칙 하나가 세 방식에서 어디에 앉는가. 각 위치가 무엇을 쉽게 만드는가 (§2)
- "TCA는 보일러플레이트가 많다"를 화면당 코드량으로 확인할 수 있었는가 (§2)
- 컴파일 시간 축에 수치를 적지 않은 이유 (§2)
- `send`와 `receive`를 나누는 것이 왜 개념적으로 중요한가 (§3)
- 처리하지 않은 효과를 실패로 만들면 어떤 버그가 막히는가 (§3)
- 순환 의존과 형제 간 방향 위반 중 무엇이 자동으로 막히는가 (§5)
- "TCA를 쓴다"와 "리듀서 패턴을 쓴다"를 분리할 수 있는 근거 (§4)
