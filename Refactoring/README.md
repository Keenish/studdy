# 레거시 → 최신 아키텍처 대규모 리팩토링

[study_list.md §5](../study_list.md#5-레거시--최신-아키텍처-대규모-리팩토링) 묶음. Phase 4.

> **읽기 전용 트랙 — 실습하지 않는다.** 규모·조직·기간이 조건이라 개인 실습으로 재현되지 않는다. 공개된 회사 사례를 읽고 의사결정 근거와 어휘를 갖추는 것이 목표.

**통과 기준**: "지금 이 코드베이스를 재작성해야 하나?"에 사례를 근거로 답할 수 있다.

## 결론 요약

실제 코드베이스를 측정해 통과 기준에 답했다 — **코드 구조 기준으로 재작성 대상 아님.** 대상이 비공개라 수치는 싣지 않고 방법과 판정 모양만 남겼다.

| 이행 축 (study_list §5-F) | 판정 |
|---|---|
| UIKit → SwiftUI | 이미 이행됨 |
| RxSwift → Concurrency | 이미 이행됨 |
| 싱글톤 → DI | 부분 — 절반 이상이 이미 actor·Sendable로 격리돼 있었다 |
| 거대 ViewController 분해 | 해당 없음 |

측정 방법은 [문서 §3](phase4-large-scale-refactoring.md#3-적용--절차를-실제-코드베이스에-돌렸다)에 명령까지 남겨 뒀다 — 다른 코드베이스에서 그대로 재현할 수 있다.

싱글톤은 **개수가 아니라 격리 방식**이 판정을 결정한다. 분류 기준은 [§5](phase4-large-scale-refactoring.md#5-중간-상태인가-정착-상태인가), 재현은 `python3 Refactoring/code/phase4/classify_singletons.py <경로>`.

운영·조직 지표(빌드 시간·크래시율·배포 주기·온보딩 비용)는 확인하지 않았다. 답의 범위가 코드 구조로 한정된다.

## 이번에 나온 발견

**일반 체크리스트가 코드베이스 상태를 암묵적으로 가정한다.** study_list §5-F의 이행 축 4개 중 2개는 이미 완료, 1개는 해당 없음이었다. 목록만 보고 착수하면 의도된 경계(채팅의 UIKit 14개)를 부수는 작업이 된다. 그래서 결정 절차의 0번이 "측정"이다.

## 원문 재검증에서 나온 것 (2026-07-31)

"사례 5건이 재검증되지 않은 요약"이라던 약점을 닫았다. 확인 14건, **정정 4건** ([문서 §8](phase4-large-scale-refactoring.md#나머지-5건-원문-재검증-2026-07-31)).

정정 4건이 전부 같은 종류였다 — **요약은 압축하면서 조용히 각색된다.**

- 계획대로 지킨 날짜가 **슬립**으로
- IPO 6개월 후가 **"직후"**로
- VP of Engineering이 **"최고 기술 책임자"**로
- 별개의 두 사실(2주에 한 번 배포 / 잦은 장애)이 **"2주마다 배포 장애"** 하나로

어느 것도 큰 거짓말이 아니라서 다시 읽지 않으면 안 잡힌다. 그중 Uber 건은 **교훈의 방향을 바꿨다** — 날짜를 못 지켜서 망한 게 아니라 지키느라 나머지가 휘었다.
